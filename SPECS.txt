Pada Milestone 1, kalian telah membangun fondasi Database Management Platform 
untuk mengatur akses, mengeksplorasi database, dan menjalankan migration 
dengan riwayat yang linear. 
Pada milestone ini, kembangkan platform tersebut agar perubahan database 
dapat divalidasi, ditinjau, dan dapat menangani migration besar secara 
asynchronous. 
Platform juga harus mendukung rollback terhadap migration yang telah berhasil 
diterapkan dan forward untuk menerapkan kembali perubahan. Keberhasilan 
eksekusi migration tidak selalu berarti aplikasi kompatibel dengan kondisi 
database yang baru. Perubahan schema maupun data dapat menyebabkan 
aplikasi gagal berjalan meskipun migration berhasil. Terutama ketika database 
digunakan bersama, setiap pemilik aplikasi atau service perlu memvalidasi 
kompatibilitas perubahan sebelum migration diterapkan. 
Riwayat eksekusi harus tetap utuh meskipun antarmuka menyediakan pilihan 
untuk menyembunyikan migration yang telah dibatalkan. Pilihan arsitektur yang 
digunakan kemudian dievaluasi melalui automated testing dan pengujian performa.

● Seluruh frontend SPA wajib responsif dan dapat digunakan pada desktop

● Automated testing wajib disediakan untuk setiap fitur backend yang relevan:

Frontend: Single-Page Application (SPA) 
Pada pendekatan server-side rendering, server dapat perlu menunggu 
pengambilan data dan pembuatan HTML sebelum mengirim halaman. Ketika 
pemrosesan lama, pengguna dapat merasakan jeda sebelum melihat tampilan. 
SPA memungkinkan navigasi dan pembaruan data tanpa memuat ulang seluruh 
halaman. Tampilan dapat menampilkan loading state terlebih dahulu, kemudian 
memperbarui isinya ketika data tersedia. SSR atau static site generation (SSG) tetap 
dapat digunakan untuk tampilan awal (kebutuhan SEO juga). Lihat MDN — 
Single-page application.

Rollback dan Forward Migration & Migration History 
Rollback migration membatalkan perubahan yang sudah berhasil di-commit 
menggunakan SQL down yang telah didefinisikan migration. Ini berbeda dari rollback 
transaction ketika eksekusi SQL gagal. Forward menjalankan kembali SQL up setelah 
migration di-rollback. 
● Rollback hanya dapat dilakukan pada migration aktif terakhir (apabila 
reversible). Untuk urutan A → B → C, rollback C harus berhasil sebelum 
rollback B. 
● Migration memiliki SQL up dan down, atau ditandai irreversible beserta 
alasannya. SQL up berisi perintah untuk menerapkan perubahan pada 
struktur atau data dalam database, sedangkan SQL down berisi perintah 
untuk membatalkan perubahan yang dilakukan oleh SQL up (rollback). 
Migration yang irreversible tidak dapat di-rollback. 
● SQL up dan down pada definisi migration yang pernah dieksekusi bersifat 
immutable. Jika perlu diperbaiki, buat migration baru; SQL tersebut tidak 
boleh ditimpa atau diganti pada pengajuan rollback maupun forward. 
● Rollback menggunakan SQL down asli dari revisi migration yang dieksekusi. 
SQL down tidak menjamin pemulihan data yang telah dihapus (untuk case 
seperti ini sebaiknya ditandai sebagai migrasi irreversible). 
● Rollback dan forward merupakan eksekusi baru. Forward mengikuti urutan 
linear dan tidak otomatis menjalankan migration berikutnya. 
● Semua eksekusi dan attempt, Semua eksekusi dan attempt, termasuk 
rollback, forward, retry, serta kegagalan, wajib dicatat. 
○ Log aplikasi: catat semua attempt, termasuk yang gagal, 
menggunakan library logging Go, misalnya log/slog, dengan output ke 
stdout/stderr. Log ini tidak disimpan di database platform. Jika 
mengerjakan bonus observability, log dapat dikumpulkan melalui 
OpenTelemetry Collector dan diteruskan ke backend log terpusat. 
○ Migration history: mencatat semua yang dieksekusi (berhasil maupun 
gagal). 
Catat migration ID, execution ID, versi/revisi migration, pengguna, waktu, status, 
serta salinan query SQL yang benar-benar dijalankan pada setiap attempt, bukan 
hanya referensi ke definisi migration. Keluarkan data ini melalui log aplikasi untuk 
semua attempt; simpan juga di database sebagai migration history untuk semua 
attempt, baik berhasil maupun gagal. Catatan migration history tidak boleh 
ditimpa. Rollback yang berhasil merujuk execution ID yang dibatalkannya. 
Hide rollback 
Sediakan checkbox Hide rollback. Jika dicentang, sembunyikan pasangan eksekusi 
yang dibatalkan dan rollback sukses yang membatalkannya. Jika tidak dicentang, 
tampilkan seluruh riwayat (attempt gagal tetap tercatat, attempt gagal boleh di 
forward lagi atau dilanjutkan dengan migration lain). 
Riwayat lengkap 
A [E1] 
B [E2] 
B (rollback E2) [E3] 
B (forward) [E4] 
C [E5] 
Hide rollback 
A [E1] 
B [E4] 
C [E5] 
E2 dan E3 disembunyikan, sedangkan E4 tetap terlihat. Pasangan ditentukan 
berdasarkan execution ID, bukan nama migration. Kegagalan tetap terlihat, rollback 
gagal tidak mengubah posisi aktif, dan filter tidak menghapus data riwayat maupun 
audit log. 
Migration Workflow dan Approval 
Draft → Pending Review → Approved → Pending (Queue) → 
Running → Success / Failed 
Agar tim-tim yang menggunakan database secara bersamaan sadar atas 
perubahan yang ingin dijalankan (termasuk rollback/forward), setiap tim leader dari 
setiap tim yang memiliki akses ke database (view dan view+edit) perlu 
meng-approve perubahan yang ingin dijalankan (pending review) (jika hanya 
digunakan 1 tim maka hanya perlu approval dari tim leadernya). 
● Setiap group memiliki leader yang ditetapkan. 
● Setiap perubahan database, termasuk rollback/forward, wajib mendapat 
approval dari leader setiap group yang memiliki akses ke database tersebut, 
baik view maupun view+edit. 
Asynchronous Processing Migration 
Semakin besar data, semakin berat pemrosesan pada DBMS. Sebagai contoh, 
memperbarui 100 juta row dapat membutuhkan waktu lama sehingga menunggu 
seluruh eksekusi selesai dalam request HTTP kurang sesuai. 
Untuk menyeragamkan interaksi, setiap eksekusi migration wajib dipublikasikan 
sebagai job ke queue dan dijalankan secara asynchronous oleh worker, termasuk 
rollback dan forward. API mengembalikan job ID tanpa menunggu SQL selesai, lalu 
pengguna memantau statusnya melalui SPA. 
Mode Eksekusi 
● Migration biasa: worker menjalankan SQL tanpa memecahnya menjadi 
batch. Mode ini tetap asynchronous melalui queue. 
● Migration per batch: worker memproses data secara bertahap dengan 
ukuran batch yang dapat dikonfigurasi. Query harus dirancang untuk 
batching; platform tidak diwajibkan memecah sembarang SQL secara 
otomatis. 
Dukung sedikitnya satu migration data besar dalam mode per batch, tanpa 
memuat seluruh dataset ke memory. Setiap batch menggunakan transaction 
tersendiri dan di-commit setelah berhasil. Jika satu batch gagal, hanya 
transaction batch tersebut yang dibatalkan; batch sebelumnya tetap committed. 
Tampilkan jumlah batch/row yang sudah committed dan status partial jika proses 
belum selesai. 
Ketentuan Pengujian 
Untuk pengujian, wajib siapkan data dengan jumlah row yang cukup besar hingga 
satu query UPDATE yang memperbarui seluruh row tanpa batching membutuhkan 
waktu lebih dari 1 detik pada lingkungan pengujian. Catat jumlah row dan durasi 
eksekusinya, lalu gunakan dataset yang sama untuk menguji migration per batch. 
Hint Implementasi Batch 
UI dapat menyediakan batch by attribute (kolom unik dan tidak berubah, misalnya 
id) dan batch size. Gunakan cursor: WHERE id > last_id ORDER BY id LIMIT batch_size. 
Tentukan cakupan target sejak awal dan susun SQL agar hanya memproses batch 
terpilih. Simpan checkpoint (execution, batch, dan cursor) bersama perubahan 
batch dalam transaction yang sama sebelum commit. 
Retry dan Pembatalan Migration Batch 
● Melanjutkan dari checkpoint: proses batch yang belum committed, tanpa 
mengulang batch yang sudah selesai. 
● Batalkan batch committed: jalankan SQL down yang immutable dan telah 
disetujui, dalam urutan batch terbalik. Simpan cakupan row dan data 
pemulihan yang diperlukan. Jika pembatalan tidak aman, tolak dan buat 
migration perbaikan baru. 
● Pembatalan adalah kompensasi per batch, bukan rollback transaction total. 
Jika gagal sebagian, simpan checkpoint dan tampilkan partially reverted 
agar dapat dilanjutkan. Kedua tindakan tetap mengikuti permission, validasi, 
dan approval. 
Concurrency dan Failure Handling 
● Satu database hanya menjalankan satu migration; database berbeda dapat 
diproses parallel. Lock berlaku lintas worker dan tetap melindungi migration di 
antara commit batch. 
● Job dan checkpoint tetap tersedia setelah restart. Retry kegagalan sementara 
dibatasi dan diberi jeda; pesan duplikat tidak boleh menyebabkan double 
commit. 
● Jika hasil commit belum pasti, periksa bukti eksekusi sebelum retry. Tahan 
migration berikutnya pada database yang sama selama hasil belum pasti 
atau migration masih partial. Jelaskan pemulihan lock ketika worker gagal. 
Activity Logging dan Tracing 
Gunakan structured log JSON melalui library logging Go ke stdout/stderr. Catat 
aktivitas penting dan setiap eksekusi SQL, termasuk query read-only, batch, retry, 
serta kegagalan. Log tidak disimpan di database platform dan tidak wajib 
ditampilkan melalui SPA. 
● Atribut: waktu, level, event, actor, database, status, dan ID korelasi. Untuk SQL, 
tambahkan query, parameter, durasi, jumlah row jika tersedia, error/SQLSTATE, 
serta migration/job/execution ID dan attempt/batch jika relevan. Catat mulai, 
hasil eksekusi, serta commit/rollback secara terpisah. 
● Tracing OpenTelemetry: hubungkan API → queue → worker → lock → 
batch/query database. Propagasikan trace context melalui queue dan 
sertakan trace_id/span_id pada log terkait. Catat durasi dan error pada 
span. 
● Samarkan credential, session identifier, dan data sensitif. Sertakan contoh 
output log dan span; exporter console boleh digunakan. Pengumpulan 
melalui Collector dan penyimpanan terpusat tidak diwajibkan (bonus).

Stress Testing dengan k6 
Lakukan stress testing menggunakan k6 dengan meningkatkan beban secara 
bertahap di atas beban normal yang ditetapkan tim, lalu turunkan kembali untuk 
mengamati pemulihan sistem. 
Uji akses API dan pengiriman job migration secara bersamaan pada database yang 
sama maupun berbeda. Gunakan migration yang sudah mendapat approval dan 
pantau status job hingga selesai. 
Catat response time API (p50 dan p95), throughput request, error rate, waktu 
tunggu queue, serta durasi dan throughput penyelesaian job. Respons pengiriman 
job tidak dihitung sebagai keberhasilan eksekusi migration. Tetapkan threshold k6 
untuk p95 response time API dan error rate, lalu jelaskan scriptnya secara singkat 
dan hasil + analisisnya pada setiap tingkat beban pada README. 
Security: SAST dengan CodeQL 
Menurut OWASP, SAST merupakan salah satu metode pemeriksaan keamanan yang 
menganalisis kode tanpa menjalankan aplikasi; metode lain, DAST, menguji aplikasi 
saat berjalan melalui request dan respons. Bonus ini menggunakan CodeQL,  tool 
SAST yang mengubah kode menjadi database analisis lalu menjalankan query untuk 
mencari potensi kerentanan, termasuk melalui penelusuran aliran data. Sebagai 
pengenalan risiko keamanan web, lihat OWASP Top 10, daftar sepuluh kategori risiko 
utama keamanan aplikasi web 
Aktifkan Static Application Security Testing (SAST) menggunakan CodeQL pada 
repository dan sertakan bukti hasil scan. 
● Dokumentasikan setiap temuan: rule, severity, lokasi kode, potensi dampak, 
serta keputusan perlu diperbaiki atau tidak beserta alasannya, misalnya 
temuan valid, false positive, atau risiko yang diterima. 
● Untuk temuan yang perlu diperbaiki, lakukan perbaikan dan sertakan referensi 
commit serta hasil scan ulang. Temuan yang tidak diperbaiki harus memiliki 
alasan yang dapat dipertanggungjawabkan. 
● Jika tidak ada temuan, dokumentasikan cakupan kode yang dianalisis dan 
hasil scan; hasil bersih tidak berarti aplikasi pasti aman.
